# 从零搭建到团队交付：JobAgent × GitHub × VS Code × Claude Code 完整协作指南

> 适用场景：多人共同开发一个网站，由负责人维护整体框架，成员分别负责功能模块，并通过 Claude Code 辅助分析、编码、检查和 Git 操作。

配套可复制 Prompt：[AI 编程团队协作必备 Prompt（通用版）](./AI_CODING_TEAM_ESSENTIAL_PROMPTS.md)

## 0. 先看结论：团队真正使用的是这一条流水线

```text
main（稳定、可展示、阶段性发布）
  ↓ 每轮开始时由负责人同步
feature/integration（公共底座、功能集成、全站联调）
  ↓ 成员开始任务前同步到自己的功能分支
feature/*（成员实际开发的功能分支）
  ↓ 本地修改 → 人工验收 → commit → 检查远程 → push
GitHub 上的远程 feature/*
  ↓ Pull Request，base 选 feature/integration
feature/integration（负责人审核、合并、联调）
  ↓ 所有功能与全站流程验收通过后创建最终 Pull Request
main
```

把它缩成一句话：

> 成员从 `integration` 获取最新公共版本，在自己的 `feature` 分支开发；功能完成后先进入 `integration` 联调，整轮稳定后再由负责人把 `integration` 合入 `main`。

这套设计解决了三个最常见的问题：

1. 成员不会直接把半成品放进正式版本。
2. 不同功能可以并行开发，又能在发布前组合测试。
3. 即使 AI 修改了代码，也必须经过差异检查、人工验收和 PR 审核。

## 1. 四个必须先理解的概念

### 1.1 仓库 Repository

仓库是整个项目及其版本历史。GitHub 保存的是远程仓库；每位成员电脑上保存的是一个本地克隆。

网页下载 ZIP 不等于克隆仓库。ZIP 通常没有 `.git` 历史，不能正常同步、提交和推送。

### 1.2 分支 Branch

分支是同一套项目历史中的一条开发路线，不是一个单独的业务文件夹。

- 同一个本地项目文件夹可以切换不同分支。
- 切换分支后，文件夹中的代码会变成该分支对应的版本。
- 每条功能分支都包含完整网站，并不是只包含它负责的页面。
- 成员可以运行整站，但只应修改自己负责的模块。

### 1.3 提交 Commit

Commit 是保存在本地 Git 历史中的一次版本快照。

- 修改文件不等于 commit。
- commit 不等于 push。
- commit 后仍然只在本机，除非继续 push 到 GitHub。

### 1.4 Pull Request（PR）

PR 不是“下载代码”的 pull，也不是 commit 或 push。

PR 是在 GitHub 上提出的合并申请：请求审核者把一个分支的提交合入另一个分支。

```text
成员功能 PR：base = feature/integration，compare = 成员的 feature/*
最终发布 PR：base = main，compare = feature/integration
```

创建 PR 不等于已经合并。只有审核并点击合并后，目标分支才真正发生变化。

## 2. 为什么不让所有人直接修改 main

如果五个人都直接向 `main` 开发，会出现以下问题：

- 未完成页面可能立刻影响全组演示。
- 两个人同时修改公共布局时，很难判断应该保留谁的版本。
- AI 可能扩大修改范围，造成与任务无关的变化。
- 很难单独审核一个功能到底改了什么。
- 出现问题时，不容易定位是哪个功能引入的。

因此 JobAgent 使用三层分支：

| 分支类型 | 含义 | 谁使用 | 允许做什么 |
| --- | --- | --- | --- |
| `main` | 稳定、可演示的阶段版本 | 全组读取，负责人发布 | 只接受经过集成验收的最终 PR |
| `feature/integration` | 下一版的集成与联调环境 | 负责人维护，成员同步 | 接收功能 PR、解决公共接口问题、运行全站验收 |
| `feature/*` | 具体功能的开发环境 | 对应功能成员 | 编写、测试并推送本模块代码 |

`feature/integration` 可以理解为“下一版 `main` 的候选版本”或“发布前集成区”，但不应把它当作随意堆代码的草稿箱。进入其中的功能也应该已经通过本模块检查。

## 3. JobAgent 的功能分支设计

项目可以按产品页面和能力边界拆分：

| 分支 | 主要目标 | 典型负责内容 |
| --- | --- | --- |
| `feature/integration` | 公共底座和全站联调 | 公共布局、共享状态、数据契约、跨模块协调 |
| `feature/dashboard` | 工作台首页 | 总览、进度摘要、核心入口 |
| `feature/resume-parser` | 简历解析 | 上传、OCR、文本提取、结构化编辑 |
| `feature/resume-optimizer` | 简历优化 | 改写建议、版本对比、针对岗位优化 |
| `feature/jd-parser` | JD 解析 | JD 获取、拆解、岗位信息提取 |
| `feature/job-analysis` | 岗位分析 | 岗位画像、要求分层、能力维度 |
| `feature/match-analysis` | 匹配分析 | 简历与 JD 匹配、差距和定制建议 |
| `feature/result-page` | 结果展示 | 分析结果汇总、展示和相关跳转 |
| `feature/application-board` | 投递看板 | 投递记录、流程状态和看板 |
| `feature/interview-coach` | 面试教练 | 问题练习、回答反馈和面试准备 |

分支数量不必等于成员数量。一名成员可以负责多个紧密相关的分支，但同一项工作必须明确：

- 当前在哪条分支；
- 本轮允许修改哪些目录；
- 哪些文件属于其他负责人；
- PR 最终合入哪里。

### 3.1 为什么成员同步 integration 后仍不能随意修改其他模块

同步的目的，是让成员拿到完整网站和已经通过集成的其他功能，从而能够联调自己的模块。

它只授予了“看到和使用这些代码”的能力，并没有改变团队职责：

- 可以运行其他页面；
- 可以读取已有接口；
- 可以检查自己的功能是否影响全站；
- 不应重构、删除或格式化其他成员的代码；
- 必须修改公共文件时，先找负责人和相关模块成员确认。

这和现实中的办公室相似：你拿到了完整项目，并不等于每个区域都由你负责。

## 4. 负责人从零搭建仓库

### 4.1 先搭建可运行的最小框架

负责人应先建立能运行的公共底座，包括：

- 项目框架和基本目录；
- 首页、导航和公共布局；
- 页面路由占位；
- 共享类型和数据契约；
- `.gitignore`；
- README 和团队协作文档；
- 最小演示数据或空状态。

框架阶段不要提前替所有成员实现完整业务。负责人提供的是统一边界、统一入口和可联调的基础。

### 4.2 建立 GitHub 仓库

负责人需要：

1. 在 GitHub 创建仓库，设置合适的公开或私有权限。
2. 把本地项目关联到正确的远程仓库。
3. 确认远程名称为 `origin`。
4. 将稳定底座放入 `main`。
5. 从稳定版本建立 `feature/integration`。
6. 从统一基线建立各个 `feature/*` 分支。
7. 在仓库设置中邀请成员为 Collaborator。

邀请成员时只需要对方的 GitHub 用户名。成员本人应登录 GitHub 接受邀请；不要通过聊天发送密码、验证码或 Token。

### 4.3 初始分支必须基于同一个底座

建立分支时应先保证所有功能分支都含有相同的公共框架。这样成员第一次克隆后，无论切到哪条功能分支，都能运行完整网站。

后续不要求所有功能分支的最新提交永远完全相同，因为每条分支会产生自己的功能代码；要求的是每次任务开始前都同步最新的 `feature/integration`。

### 4.4 负责人应提前定义共享修改热点

JobAgent 中常见的公共文件包括：

- `src/app/layout.tsx`
- `src/app/globals.css`
- `src/components/layout/`
- `src/lib/store.tsx`
- `src/types/analysis.ts`
- `src/lib/schemas/analysis.ts`
- `package.json`
- `package-lock.json`
- `next.config.ts`

修改这些文件可能同时影响多个页面，所以功能成员必须在 PR 中单独说明原因。

## 5. 成员第一次加入项目

### 5.1 准备条件

每位成员需要：

1. GitHub 账号；
2. 已接受私有仓库邀请；
3. Git；
4. VS Code；
5. 项目约定的 Node.js 环境；
6. Claude Code（如果团队使用 AI 辅助）；
7. 自己负责的功能分支名称和目录范围。

GitHub MCP 不是必需条件。没有 MCP，成员仍可以：

- 在 VS Code 中克隆和同步代码；
- 使用 Git 提交和推送；
- 在 GitHub 网页创建、审核和合并 PR。

### 5.2 在 VS Code 登录 GitHub

1. 点击 VS Code 左下角的“账户”。
2. 选择使用 GitHub 登录。
3. 在浏览器确认网址属于 `github.com`。
4. 由成员本人完成登录和授权。
5. 不把密码、验证码、Cookie 或 Token 发给 AI。

### 5.3 正确克隆，而不是下载 ZIP

在 VS Code 中选择“克隆 Git 存储库（Git: Clone）”，输入：

```text
https://github.com/mrblank965/JobAgent.git
```

选择本地保存位置后打开项目。不要点击“Publish to GitHub”来连接已经存在的 JobAgent；该入口主要用于把一个本地项目发布成新仓库。

### 5.4 选择远程功能分支

克隆后，VS Code 左下角通常显示当前分支。点击分支名称，在远程分支列表中选择自己的 `origin/feature/...`。

首次选择远程分支时，VS Code 通常会在本地创建一条跟踪分支。之后点击不同本地分支，就是在同一个项目文件夹中切换不同版本，不会自动多出一个业务文件夹。

### 5.5 第一次只做连接检查

把下面的 Prompt 发给 Claude Code：

```text
请只检查当前 JobAgent 项目与 GitHub 的连接状态，暂时不要修改代码、提交、推送或安装工具。

请依次检查并用中文解释：
1. 当前文件夹是否是真正的 Git 仓库，而不是网页下载的 ZIP。
2. Git 是否已经安装并可用。
3. 当前仓库的远程地址是否指向：
   https://github.com/mrblank965/JobAgent.git
4. 远程名称是否为 origin。
5. 当前分支是什么。
6. 是否能读取远程分支列表。
7. Git 提交身份 user.name 和 user.email 是否已经配置。
8. 工作区是否有未提交修改。
9. 是否能看到 main、feature/integration 和我负责的远程功能分支。

安全规则：
- 不读取或展示 .env.local。
- 不搜索或显示 API Key、GitHub Token、密码和浏览器 Cookie。
- 不要求我把密码、验证码或 Token 发到对话框。
- 不自动创建新的 GitHub 仓库。
- 不执行 git init、强制推送、重置、删除分支或覆盖文件。
- 如果需要登录，只告诉我在 VS Code 的哪个位置操作，由我本人完成浏览器授权。

最后用表格汇报：检查项目、当前结果、是否需要我操作、下一步。
```

### 5.6 Git 提交身份由成员本人决定

`user.name` 和 `user.email` 是提交历史中的作者信息，不是 GitHub 密码。AI 不应编造姓名或邮箱，也不应自动使用其他成员的信息。

如果未配置，应停止提交，让成员本人决定使用 GitHub 已验证邮箱或 GitHub 提供的 no-reply 邮箱。优先只在当前仓库配置，避免意外影响电脑上其他项目。

### 5.7 截图版：成员使用 VS Code 的六步流程

下面是一套更适合第一次参与项目成员的按钮式流程。它和后文的完整安全流程一致；遇到分支、远程差异或冲突不确定时，先让 Claude Code 检查，不要凭感觉点按钮。

#### 第一步：确认并切换到自己的功能分支

成员电脑中通常只有一个 `JobAgent` 项目文件夹。先看 VS Code 左下角的分支名称，确认它是自己负责的 `feature/*`，不要在 `main` 或 `feature/integration` 上直接开发。

如果本地还没有自己的功能分支，可以点击左下角分支名称，并选择对应的 `origin/feature/...`。VS Code 通常会基于远程分支建立本地跟踪分支并切换过去。

> 这里不是为每个分支重新下载一份项目。所有分支仍然在同一个 `JobAgent` 文件夹中，切换分支会让文件显示为该分支的版本。

![图 1：在 VS Code 中选择自己的功能分支](./assets/vscode-team-workflow/01-select-feature-branch.png)

#### 第二步：开工前同步远程最新状态

左下角的循环箭头是“同步更改”按钮。它可能同时执行拉取和推送，不是一个只负责下载的按钮。

如果当前没有本地新提交、工作区也干净，可以用它同步当前远程同名分支。VS Code 出现“将从远程拉取并向其推送提交”的确认框时，要再次核对弹窗中的远程分支名称是否正是自己的分支。

![图 2：VS Code 的同步确认提示](./assets/vscode-team-workflow/02-sync-changes-confirmation.png)

但成员开工前真正需要确认的不只是远程同名分支，还包括最新的 `origin/feature/integration`。因此更推荐先把第 6.2 节的“安全同步最新 integration”Prompt 发给 Claude Code。AI 应先检查分支、工作区和远程差异，再决定是否可以同步。

![图 3：让 Claude Code 检查并同步最新 integration](./assets/vscode-team-workflow/04-sync-integration-prompt.png)

如果弹窗、箭头数字或同步结果看不懂，可以发送：

```text
请先不要修改、提交或推送。检查我当前的 Git 分支、工作区、远程同名分支和 origin/feature/integration，告诉我 VS Code 左下角“同步更改”按钮现在会执行什么，以及是否可以安全点击。如果有未提交修改、远程新提交或可能冲突，请停止并说明，不要自动处理。
```

#### 第三步：先发送共同规则，再布置具体任务

每次新建 Claude Code 会话时，先发送本文第 6.3 节的“共同工作规则”。这段规则只需发送一次，后续可以用简短 Prompt 布置任务。

共同规则的作用是告诉 AI：当前角色、分支、负责范围、安全限制和工作顺序，避免它越过职责边界或在验收前提交代码。

![图 4：共同工作规则 Prompt](./assets/vscode-team-workflow/03-common-prompt.png)

#### 第四步：修改代码并检查“源代码管理”中的文件

与 Claude Code 对话并确认方案后，AI 可能修改现有文件，也可能新增组件。点击 VS Code 左侧的“源代码管理”图标，可以在“更改”区域看到本轮涉及的文件。

![图 5：VS Code 源代码管理区域](./assets/vscode-team-workflow/05-source-control-changes.png)

常见状态字母包括：

- `M`：已有文件被修改；
- `U`：新文件尚未被 Git 跟踪；
- `A`：新文件已经加入本次提交；
- `D`：文件被删除。

颜色会因 VS Code 主题而变化，所以不要只根据“绿色”判断。应逐个打开差异，确认它们都属于本轮任务，再输入准确的提交说明并点击“提交”。

> “提交”只是把当前修改保存为本地功能分支上的一个 Commit，还没有上传到 GitHub。

#### 第五步：Commit 后同步到远程同名功能分支

Commit 完成后，VS Code 左下角可能出现向上箭头或 `1↑`，表示本地有一个或多个 Commit 尚未上传。再次点击循环箭头“同步更改”时，VS Code 通常会：

1. 获取并拉取远程同名分支的新提交；
2. 再把本地 Commit 推送到远程同名分支。

![图 6：Commit 后同步本地与远程功能分支](./assets/vscode-team-workflow/06-sync-after-commit.png)

点击前应先执行本文第 11 节的“推送前远程检查”。如果别人已经更新了远程同名分支：

- 普通 Push 通常会被拒绝；
- 需要先拉取并安全合入远程修改；
- 同一位置存在不同修改时可能产生冲突；
- 不允许使用强制推送覆盖他人提交。

Push 只更新 GitHub 上的远程功能分支，不会自动修改 `feature/integration` 或 `main`。

#### 第六步：创建 Pull Request

本地 Commit 已经推送到远程同名功能分支后，才能申请把它合入 `feature/integration`。可以把下面这个简短 Prompt 发给 Claude Code：

```text
请为当前功能分支创建 Pull Request。

1. 先确认当前分支、工作区状态以及远程同步状态。
2. 确认当前修改已经提交并推送到远程同名分支。
3. 如果远程存在其他成员的新提交，先停止并向我汇报，不要强制推送。
4. 将当前功能分支作为来源分支。
5. 将 feature/integration 作为目标分支。
6. 根据实际修改整理清晰的 PR 标题和说明，包括修改内容、检查结果和人工验收方法。
7. 只创建 Pull Request，不要合并。
8. 不要向 main 直接创建 PR，不要使用强制推送。
9. 创建完成后，把 PR 链接发给我，等待负责人审核。
```

更完整的检查版本见本文第 13.2 节。如果 Claude Code 没有可用的 GitHub 工具，也可以让它只生成 PR 文案，再由成员在 GitHub 网页手动创建。

## 6. 每次开始工作的标准步骤

### 6.1 先确认自己站在哪里

开始任何操作前确认：

- 当前打开的是 JobAgent 仓库；
- 当前分支是自己的功能分支；
- 工作区是否干净；
- 远程跟踪分支是否正确；
- 没有其他成员遗留的本地修改。

如果工作区有未提交修改，不要直接切分支、拉取或覆盖。先判断这些修改是谁的、是否完成、是否需要提交。

### 6.2 安全同步最新 integration

成员并不是把所有其他功能分支逐个拉到本地，而是同步已经被负责人接受进 `feature/integration` 的内容。

使用这个 Prompt：

```text
请先不要实现功能，把 origin/feature/integration 的最新版本安全同步到我当前的功能分支。

我的功能分支是：【填写功能分支】
我的负责范围是：【填写允许修改的目录或文件】

1. 先确认当前分支和工作区状态。
2. 如果有未提交修改，立即停止，不要自动暂存、覆盖或丢弃。
3. 获取远程最新状态。
4. 使用不改写历史的方式合入 origin/feature/integration。
5. 同步 integration 是为了获得完整网站和已合并功能，不代表允许修改其他成员模块。
6. 除我的负责范围外，其他模块一律只读：可以运行、查看和调用，但不能编辑、重构、删除或格式化。
7. 如果必须修改职责范围外的文件，先列出文件、原因、影响、负责人和替代方案，然后停止等待确认。
8. 如果发生冲突，不要自动选择任何一方；列出冲突文件、双方修改和建议确认人。
9. 不向 main 或 feature/integration 推送，不使用强制推送。
10. 同步后运行 lint 和 TypeScript 检查。

最后汇报同步前后版本、冲突情况、允许修改范围、只读模块，以及现在能否开始开发。
```

```text
【明确禁止】

1. 不修改职责范围外的模块。
2. 不重写整个项目。
3. 不改变已有接口、共享类型或公共状态；如确实需要，先说明影响并等待负责人确认。

7. 不提交、不推送、不创建 PR，完成后先等待我人工验收。

【工作顺序】

在我回复“人工验收通过”之前，不要提交或推送。请记住以上规则，在我发送具体任务前不要修改代码。
```

```text
实际结果：【现象或错误原文】
```

### 7.5 为什么先分析再改代码

AI 能快速生成代码，但它可能：

- 误解已有结构；
- 为了一个小功能改动多个公共文件；
- 重写已经可用的实现；
- 安装不必要依赖；
- 把临时方案当成正式架构。

因此“分析 → 列文件 → 人确认 → 最小修改”比一句“帮我做完”更适合多人协作。

## 10. Commit：先在本地保存一个清晰版本

```text
6. 再运行 lint、TypeScript 检查、相关测试和生产构建。

9. 不向 main 或 feature/integration 直接提交或推送，不强制推送，不删除分支。
```

## 11. Push 前为什么必须再次检查远程

设想两个人同时维护 `feature/match-analysis`：

```text
上午：两个人都从提交 A 开始
同学 1：A → B，并先 push
同学 2：A → C，此时远程已经是 B
```

同学 2 普通 push 时，Git 通常会拒绝，因为远程包含本地没有的提交 B。它不会悄悄用 C 覆盖 B。

正确做法是：

```text
获取远程 B → 安全合入本地 C → 有冲突则人工判断 → 检查 → 普通 push
```

错误做法是为了绕过拒绝使用强制推送。强制推送可能改写远程历史，导致同学 1 的提交消失，因此团队规则必须明确禁止。

推送前 Prompt：

```text
我准备把当前修改推送到远程同名功能分支，但可能有其他成员已经更新了远程分支。

请先不要推送。

1. 检查当前分支和未提交修改。
2. 获取远程最新状态。
3. 比较本地分支与远程同名分支，同时比较当前分支与 origin/feature/integration。
4. 分别列出远程同名分支新增提交、integration 新增提交和本地新增提交。
5. 如果远程同名分支有新提交，使用不改写历史的方式安全合入本地。
6. 如果 integration 有尚未进入当前分支的新提交，也安全合入本地。
7. 如果发生冲突，不要自动选择任何一方；列出冲突文件、双方修改和对应负责人，等待确认。
8. 合并完成后运行 lint、TypeScript 检查和生产构建。
9. 只有远程同名分支和 integration 都已安全同步且检查通过，才告诉我可以推送。
10. 不使用强制推送，不覆盖远程历史；完成检查后先汇报，不要直接推送。
```

如果同一功能需要多人长期同时开发，最好再拆成更小的任务分支，而不是所有人持续向同一条功能分支 push。

---

## 12. Push：把本地提交上传到远程同名分支

```text
推送前远程检查已经通过。请把当前本地提交推送到远程同名功能分支。

1. 再次确认当前分支是【功能分支】，且不是 main 或 feature/integration。
2. 确认工作区干净，并与刚刚检查的远程状态一致。
3. 使用普通推送，将当前分支推送到 origin 的同名功能分支。
4. 如果推送被拒绝，立即停止，重新获取远程状态并汇报差异；不要改用强制推送。
5. 不创建名称相近的新分支，不向 main 或 feature/integration 推送，不删除或覆盖远程分支。

最后告诉我远程分支名称、推送的提交编号和结果。不要自动创建或合并 Pull Request。
```

### 12.1 VS Code 的“同步更改”按钮是什么意思

VS Code 左下角的循环箭头通常表示同步：它可能先拉取远程提交，再推送本地提交。

它不是单纯的 commit，也不等于 PR。不要在以下情况下盲目点击：

- 当前分支不确定；
- 工作区还有未提交修改；
- 不清楚远程是否被他人更新；
- 出现冲突但尚未确认保留哪一方。

更安全的顺序仍是：先检查分支和远程差异，再 commit，再普通 push。

## 13. 创建功能 PR：feature → integration

完成 push 后，成员在 GitHub 创建 Pull Request：

```text
base: feature/integration
compare: 自己的 feature/*
```

例如匹配分析成员应选择：

```text
base: feature/integration
compare: feature/match-analysis
```

成员不能把功能 PR 直接指向 `main`，否则会绕过集成联调。

### 13.1 不安装插件也能创建 PR

在 GitHub 网页操作：

1. 打开仓库；
2. 点击 Pull requests；
3. 点击 New pull request；
4. 设置正确的 base 和 compare；
5. 检查 Changed files；
6. 填写标题、说明和测试结果；
7. 点击 Create pull request；
8. 等待审核，不要立即自行合并。

也可以选择：

- VS Code 官方的 GitHub Pull Requests and Issues 扩展；
- 已安装并登录的 GitHub CLI；
- 已授权的 GitHub MCP。

它们只是不同入口，不改变 base、compare、审核和安全规则。AI 不应自行安装工具或更改认证；浏览器登录仍由成员本人完成。

### 13.2 创建 PR Prompt

```text
请为刚刚推送的功能分支创建或准备 Pull Request，暂时不要合并。

base：feature/integration
compare：【自己的功能分支】

1. 确认当前分支是 compare 指定的功能分支。
2. 获取远程最新状态，确认提交已完整推送到远程同名分支。
3. 确认 base 不是 main，compare 不是 integration。
4. 检查是否已有相同 base 和 compare 的开放 PR；如有则返回原链接，不重复创建。
5. PR 说明包含：问题、完成功能、主要文件、接口/类型/依赖变化、公共文件变化、自动检查、人工验收、安全检查、已知限制和下一步。
6. 不包含 API Key、Token、真实简历、个人隐私、.env.local 内容或本机绝对路径。
7. 已有授权工具时可以创建 PR，但不要安装工具或更改认证。
8. 只创建，不合并，并返回链接。
9. 没有创建权限时，生成完整 PR 文案，并告诉我网页操作方法。
10. 不索要密码、验证码或 Token。

最后汇报 base、compare、标题、链接，以及需要负责人特别审核的公共或跨模块变化。
```

### 13.3 PR 被要求修改怎么办

不要关闭 PR 后重新建分支。继续在原功能分支修复、commit 并 push，原 PR 会自动更新。

## 14. 审核功能 PR

审核者不应只看作者或 AI 写的“已完成”，而应检查真实差异。

```text
请以 JobAgent 审核者身份检查这个 Pull Request：【PR 链接或编号】。

暂时不要修改代码、提交、推送或合并。

请检查：base/compare、职责范围、无关修改、公共文件变化、接口和类型一致性、对其他模块的影响、正常/加载/空/错误状态、安全与隐私，以及 lint、TypeScript、相关测试和生产构建结果。

最后明确给出“可以合并到 feature/integration”“修改后再合并”或“暂缓合并”。如需修改，列出具体文件、原因和复现步骤。不要仅根据文字说明批准。
```

功能 PR 合入 integration 后，改动实际进入的是 integration 中对应的文件，而不是复制出另一套网页。Git 会根据提交中的差异修改目标分支的同路径文件。

## 15. 负责人维护 integration

### 15.1 新一轮开始前：main → integration

`main` 是上一轮稳定基线。新一轮开始时，负责人确保它已经安全进入 integration：

```text
请以 JobAgent 集成负责人身份，把远程最新 main 安全同步到 feature/integration。

1. 检查当前分支、工作区和远程状态。
2. 如有未提交修改，立即停止，不覆盖、不暂存、不丢弃。
3. 获取 origin 最新状态。
4. 切换到 feature/integration，并以不改写历史的方式同步 origin/main。
5. 如发生冲突，不自动解决；列出冲突文件和双方修改，等待确认。
6. 同步后运行 lint、TypeScript 检查和生产构建。
7. 检查通过后，将更新后的 integration 推送到远程同名分支。
8. 不向 main 直接推送，不强制推送，不删除分支。

最后汇报同步前后版本、检查结果和成员是否可以开始同步各自分支。
```

### 15.2 一轮功能合入后：integration 全站检查

```text
请以 JobAgent 集成负责人身份检查 feature/integration，暂时不要修改、提交、推送或合并。

1. 列出本轮已经合入和尚未合入的功能 PR。
2. 检查不同模块的接口、共享类型、公共状态和页面流程是否一致。
3. 检查重复实现、相互覆盖、无关修改或未确认依赖。
4. 检查敏感信息、真实简历、个人隐私和构建产物。
5. 运行完整 lint、TypeScript 检查、测试和生产构建。
6. 给出简历、JD、匹配、结果、投递和面试完整流程的人工验收清单。

最后明确给出“可以向 main 发 PR”“修复后再发 PR”或“暂缓发布”，并说明理由。不要直接合并 main。
```

### 15.3 最终 PR：integration → main

```text
集成检查和人工验收已经通过。请创建或准备本轮最终 Pull Request。

base：main
compare：feature/integration

确认所有计划内功能 PR 已进入 feature/integration，并确认 lint、TypeScript、测试、生产构建、完整流程验收和安全检查均已通过。

PR 说明应包含：本轮功能、来源 PR、主要结构变化、接口与依赖变化、自动检查、人工验收、安全检查、已知限制和下一轮计划。

只创建 PR，不要自动合并。返回 PR 链接，等待负责人本人或指定审核者确认。
```

当最终 PR 合并后，`main` 才代表这一轮的新稳定版本。

## 16. 下一轮如何重新开始

功能 PR 合入 integration 后，成员需要重新获取 integration，自己的分支才会出现其他成员已经集成的成果。

```text
我的功能 PR 已经合并到 feature/integration。请获取远程最新状态，并把 origin/feature/integration 安全同步到我当前的功能分支。

同步前先检查工作区；如果不干净就停止。不要改写历史、强制推送或自动解决冲突。同步完成后运行 lint 和 TypeScript 检查，不修改业务代码。

最后告诉我当前分支、同步结果和是否可以开始下一轮任务。
```

团队由此进入循环：

```text
同步 integration
→ 开发
→ 自查和人工验收
→ commit
→ 检查远程
→ push
→ PR 到 integration
→ 审核与联调
→ integration PR 到 main
→ 下一轮
```

## 17. 冲突和“覆盖代码”到底是怎么发生的

### 17.1 同时修改不一定马上冲突

两个人修改不同文件，Git 往往可以自动合并。两个人修改同一个文件的不同位置，也可能自动合并。

真正需要人工判断的情况通常是：

- 修改同一文件的同一段代码；
- 一个人删除文件，另一个人继续编辑；
- 两个人同时重构共享接口；
- 一个人改字段名，另一个人仍按旧字段开发；
- AI 大范围格式化，使差异远超任务本身。

### 17.2 普通 push 通常不会直接覆盖远程新提交

当远程有本地没有的提交时，普通 push 通常会被拒绝。这是一种保护机制。

危险的是：

- 使用强制推送；
- 在冲突中无条件选择“接受当前”或“接受传入”；
- 用 reset、checkout 或文件覆盖丢弃未确认修改；
- AI 未检查差异就把整份文件重写。

### 17.3 发生冲突时的原则

1. 停止自动处理；
2. 列出冲突文件；
3. 说明双方分别改变了什么业务；
4. 找到对应模块负责人；
5. 确认接口和最终用户行为；
6. 人工决定如何合并；
7. 重新运行检查和页面验收。

冲突不是错误，它是在提醒团队：两个修改同时影响了同一个决策点。

## 18. 安全与隐私底线

任何分支、commit、push 和 PR 都必须确认没有：

- `.env.local`；
- API Key、GitHub Token、密码、Cookie；
- 真实简历文件或原文；
- 姓名、手机号、邮箱等个人隐私；
- `node_modules`；
- `.next`；
- 日志、缓存和临时文件；
- 与任务无关的大文件。

额外规则：

- 不让成员把密码、验证码或 Token 发进 AI 对话框；
- 不让 AI 编造 Git 作者姓名和邮箱；
- 不在不知情的情况下安装新依赖；
- 不使用 reset、强制推送、删除分支或覆盖文件；
- 不自动创建新 GitHub 仓库；
- 不直接向 `main` 或 `feature/integration` 推送成员功能代码。

## 20. 常见问题

### Q1：点击远程分支是不是会把它下载到本地？

首次选择 `origin/feature/...` 时，VS Code 通常会创建对应的本地跟踪分支，并切换到它。仍然使用同一个项目文件夹，里面的文件会随分支切换。

### Q2：每条分支需要分别克隆一个文件夹吗？

不需要。一个克隆就能切换多个分支。高级用户可以为并行任务使用 Git worktree，但 worktree 外层文件夹只是本机组织方式，不会上传成 GitHub 仓库中的文件夹。

### Q3：成员在自己的 feature 分支能看完整页面吗？

能。每条分支都有完整项目，但只能看到该分支已经拥有的版本。其他成员尚未合入 integration 的新改动不会自动出现。

### Q4：本地分支同步到远程属于 Pull Request 吗？

不属于。把本地提交上传到远程同名分支叫 push；PR 是远程分支之间的审核与合并申请。

### Q5：点击 VS Code 的提交按钮会上传 GitHub 吗？

通常只会创建本地 commit。之后还要经过远程检查和 push，GitHub 才能看到提交。

### Q6：有人已经更新同一远程功能分支，我 push 会覆盖他吗？

普通 push 通常会被拒绝，不会自动覆盖。应先获取远程提交并安全合入本地。禁止用强制推送绕过保护。

### Q7：功能成员可以修改其他模块吗？

技术上可以打开这些文件，但团队规则上不允许。确需跨模块或修改公共文件时，应先说明影响并由负责人和对应成员确认。

### Q8：为什么不是直接从每个 feature PR 到 main？

因为单个功能测试通过不代表整站组合后没有问题。integration 提供公共联调和发布前验收层，保护 main 始终处于可展示状态。

### Q9：为什么 PR 合并后我的本地看不到？

GitHub 远程目标分支已经更新，但本地不会自动变化。需要获取远程状态，并把最新 integration 安全同步到当前功能分支。

### Q10：必须连接 GitHub MCP 才能让 Claude Code 协作吗？

不必须。最通用流程是 Claude Code 处理本地代码和检查，VS Code/Git 负责同步，GitHub 网页负责创建与审核 PR。MCP、扩展和 CLI 只是可选的效率工具。

## 21. 适合发到群里的极简版流程

```text
1. 接受 GitHub 仓库邀请，用 VS Code Clone，不下载 ZIP。
2. 切到自己的 feature 分支，一个文件夹即可，不需要重复下载。
3. 开工前确保工作区干净，把最新 feature/integration 安全合入自己的分支。
4. 新 Claude Code 会话先发送一次共同规则，再发送具体短任务。
5. AI 先分析和列文件，人确认后再改代码。
6. 运行 lint、TypeScript、测试、生产构建，并人工检查页面。
7. 验收后只 commit 到本地。
8. Push 前检查远程同名分支和最新 integration，有冲突就停下来人工确认。
9. 普通 push 到远程同名 feature，禁止强制推送。
10. 创建 PR：base = feature/integration，compare = 自己的 feature。
11. 审核通过后由负责人合入 integration 并联调整站。
12. 一轮稳定后，负责人创建 integration → main 的最终 PR。
```

## 23. 最后的协作原则

工具可以自动完成很多操作，但不应替团队做未经确认的决策。

最可靠的 AI 编程协作不是“让 AI 一次做完”，而是：

```text
边界清楚
→ 先看现状
→ 给出最小方案
→ 人确认
→ 小范围实现
→ 自动检查
→ 人工验收
→ 保存版本
→ 比较远程
→ 审核合并
```

只要全组坚持这条链路，即使成员对 Git 不熟悉，也能知道每一步正在改变什么、风险在哪里，以及出现问题时应该停在哪一步。
